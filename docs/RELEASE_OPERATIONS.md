## Backend build and traffic boundary

The prepared target is AWS Mumbai, Amazon Linux 2023: Caddy HTTPS -> Node 24 Next.js website/admin -> Python 3.12 FastAPI -> Atlas and private R2 over TLS. `deploy/compose.production.yml` publishes only Caddy TCP 80/443. API and Web have no host port bindings. API runs as UID 10001, Web as UID 1000. Images exclude environment files. Base image manifest digests are pinned in source; complete Linux validation and pin release image digests and retain the previous release. Never print interpolated Compose JSON/YAML or container environments: use `python scripts/check-production-compose.py --env-file <external-compose-settings-file>` for a sanitized offline review.

Caddy serves `landvilla.in` and redirects `www.landvilla.in` to it. HTTP redirects to HTTPS. Caddy discards client forwarding headers and sets canonical Host/scheme. Web independently generates `X-Forwarded-Proto` from validated public configuration on EVERY server API path. `WEB_ORIGIN=https://landvilla.in` is mandatory. Explicit `BACKEND_TRANSPORT=private-http` permits only `BACKEND_ORIGIN=http://api:8000`; arbitrary HTTP origins are rejected. API HTTPS enforcement remains enabled, trusting only the exact canonical RFC1918 Web IP in `FORWARDED_ALLOW_IPS`, which Compose also assigns to Web. Host/source verification on the approved host is a release gate; declaring an address is not proof. `TRUSTED_HOSTS=api,127.0.0.1` permits API service discovery and local probes. Caddy has request size/time limits; independent abuse protection remains an acceptance gate. Do not log headers, bodies, query strings or provider errors.

This is an ordinary shared Docker bridge, NOT enforcement of the separately proposed directional firewall plan. There are no subnet/IP defaults and no firewall, systemd, DNS, AWS, Atlas or R2 changes. Containers/host administrators on the bridge remain trusted; API-to-Web and Caddy-to-API blocking is unproven. See [EC2_DIRECTIONAL_ISOLATION_PLAN.md](EC2_DIRECTIONAL_ISOLATION_PLAN.md); its separate host-policy approval and testing gates remain open.

API `/health` is dependency-free process liveness; `/ready` checks Mongo ping, session-capable replica-set/sharded topology and read-only R2 HeadBucket. Web `/health` validates its fixed configuration; `/ready` checks API readiness. Caddy actively probes Web `/ready` and withdraws an unhealthy upstream after a failed check (15-second polling, not instantaneous). Caddy denies public probe routes; its own liveness listener binds only container loopback:8080. Docker health status alone does not restart unhealthy processes; `unless-stopped` restarts exited processes. Alert and investigate sustained failures. Readiness does not prove transaction privileges or object read/write rights: those require approved isolated staging tests. No production test writes. API drains for 30 seconds; Compose allows 40 seconds.

## Environment names (values belong in the secret manager)

API secret file names: MONGO_URL, DB_NAME, STORAGE_PROVIDER=cloudflare_r2, S3_ENDPOINT, S3_BUCKET, S3_ACCESS_KEY_ID, S3_SECRET_ACCESS_KEY, IDENTITY_ENABLED=true, OTP_HMAC_SECRET; optional S3_REGION. GOOGLE_CLIENT_IDS and sender credentials are required for the corresponding enabled sign-in channels. Compose fixes APP_ENV, CORS_ORIGINS, WEB_APP_ORIGINS, TRUSTED_HOSTS, PYTHON_DOTENV_DISABLED and FORWARDED_ALLOW_IPS, and disables all seeds, live payments, Play billing and refunds. Razorpay keys are blanked even if inherited from the API file. Web/Caddy never receive this API secret file. Dedicated runtime proxy credentials are separately scoped: Caddy/Web LANDVILLA_INGRESS_TOKEN and Web/API WEB_API_IP_KEY, supplied as LANDVILLA_WEB_API_IP_KEY in private Compose settings. They must be distinct random32-byte hex values, never rehearsal fixtures. CLIENT_IP_MODE=signed-v1 is mandatory. DEPLOYMENT_TIER=production requires DB_NAME=landvilla_prod and S3_BUCKET=landvilla-property-media-prod; Mongo TLS-disable/insecure options are rejected. See `deploy/.env.example` for separate nonsecret operator settings and the readiness report for exact validation requirements.

Email OTP: SMTP_HOST, SMTP_PORT, SMTP_USERNAME, SMTP_PASSWORD, SMTP_FROM. SMS OTP: TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN, TWILIO_FROM. Enable only channels with configured senders. Billing: names and permissions in MONETIZATION_SETUP.md; keep live payments/refunds disabled until policies and provider tests are approved. Native build: EXPO_PUBLIC_BACKEND_URL, existing Google client configuration. EXPO_PUBLIC values are public; never place secrets there.

## Additive index provisioning

Offline plan: `python backend/scripts/provision_release_indexes.py`. This does not import the application, load dotenv or connect. After backup, isolated staging rehearsal and explicit database authorization, inject environment securely, then run `python backend/scripts/provision_release_indexes.py --apply --confirm-database <approved-database-name>`. Repeated runs ensure existing indexes; no records/indexes are dropped and no reference/demo data is seeded. TTL indexes expire session/OTP/rate-limit records by design: review that effect before applying. Conflicts or duplicates stop safely and may leave earlier additive indexes present. Never resolve conflicts by deleting user records.

Legacy unique non-partial razorpay_order_id indexes block multiple Google Play orders without Razorpay IDs. The command refuses this state before applying indexes. Replacement requires separately approved migration after checking data; it is deliberately not automated. Existing reference locations/categories must be reviewed and provisioned separately, not startup-seeded.

## Backups, storage and deletion

Enable encrypted Atlas backups/PITR and approved retention. Record snapshot ID before release. Restore to a separate isolated cluster/database, validate counts, ownership, indexes and referential consistency with read-only scripts; never restore over live data. Drill access and recovery time before launch. Restrict backup-reader roles and audit exports; never put database URLs on a command line or into logs.

Keep the R2 bucket private: disable r2.dev and public custom domains for this shared bucket. Use least-privilege bucket-scoped credentials. Deliver files through the existing authorized API. Broker documents remain private regardless of metadata flags. HeadBucket readiness does not prove bucket privacy; review dashboard policies separately. Maintain an encrypted, access-controlled backup strategy for media; database snapshots alone do not back up R2 objects.

Account deletion currently tombstones media and hides listings, removes sessions/profile/saved data and anonymizes enquiries/payment ownership. It does NOT physically purge R2 bytes. Approve retention periods for identity documents, images, audit records, backups and statutory payment records before scheduling physical deletion. No automated purge or retention duration has been invented. Public deletion requests need a staffed ownership-verification and fulfilment process; confirm the existing 30-day promise before publication.

## Region, rollout and rollback

The owner-selected target is AWS Mumbai on Amazon Linux 2023. Account permissions, available host capacity, complete subnet collision checks, actual proxy source IP, Docker image execution, DNS and TLS remain deployment acceptance gates. The supplied EC2 inventory is documented in the isolation plan; no host or AWS calls were made for this preparation. The new ordinary bridge must not be presented as directional isolation or restricted egress.

Preflight: the sanitized Compose checker above plus `python scripts/check-production-release.py` in a securely configured shell. Do not run the monetization enablement checklist as an instruction to enable billing; billing remains disabled for this release. Before rollout: release tests, dependency/image security review, staging smoke tests, private-media checks, restore drill and operator approval. Follow the exact staged startup and rollback commands in the readiness report. Retain additive indexes and data; rollback never restores the live database or removes records. Set alerts for 5xx, readiness failures and OTP abuse without recording personal data. Native Bearer API access and payment webhooks are not supported through the browser-only proxy and require a separate approved ingress design.

Web authenticates that token, signs method/path/time/IP using a different API hop key, and never forwards the token or caller forwarding claims. API requires exact Web peer, no X-Forwarded-For, fresh valid HMAC and canonical IP before selecting the rate bucket. Host/scheme/session authorization are unchanged. Real source address and path behavior remain Linux/EC2 gates. No CDN forwarded chain is accepted. Caddy therefore receives one narrowly scoped proxy credential, not database/storage/OTP secrets.

API liveness is dependency-free only after startup; startup still fails closed on DB/index unavailability. Rehearsal uses restart=no; production unless-stopped needs restart alerts and cold-start outage testing. Google audience preflight is conditional on enabled public Google configuration. Refund operations are disabled in the browser surface and backend release flags remain false.
